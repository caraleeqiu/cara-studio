# 语音驱动 Mac：方案研究

目标一句话：**按下按键说话，Mac 就切 App、打字、点东西。** 最后再把「按键」换成一个外接硬件。

日期：2026-09-05。这份文档只定方案，不写代码。

---

## 0. 定位：一个用嘴驱动的启动器

它就是 Raycast、Alfred、Spotlight、Siri 这一类东西，**输入从打字换成说话**。想清楚这一点很重要，因为它决定了哪些不用自己做：

| 层 | 人家已经有的 | 我们做的 |
|---|---|---|
| 切 App | Spotlight、Siri、Raycast 都能 | 只是壳，顺手做，为了让后面有地方长 |
| 听写 | macOS 自带听写、Wispr Flow、WhisperDictation | 同上，做成自己的是为了能改、能接硬件 |
| 点东西、跑任务 | Siri 做不到，Raycast 只能跑预设脚本 | **这是真正的差异**：一个能看见界面、在任意 App 里操作的 Agent |
| 硬件触发 | 没有产品做 | **第二个差异**：把触发从键盘挪到桌上一个实体 |

所以①②只是启动器的地板，③④和硬件才是这个项目存在的理由。①②做得快是好事，别在上面花太多时间打磨。

---

## 1. 把需求拆成四个动作

你说的功能其实是四种不同的东西，难度差很多，得分开看：

| 动作 | 例子 | 难度 | 靠什么 |
|---|---|---|---|
| ① 切 App | 「打开微信」「切到 Chrome」 | 很低 | 系统调用一行 |
| ② 听写 | 「帮我回他：明天下午三点可以」 | 低 | 语音识别 + 粘贴到光标 |
| ③ 点东西 | 「把这封邮件归档」「点左边第二个」 | 高 | Agent 读界面、决定、执行 |
| ④ 执行任务 | 「把这页存成 PDF 发给老张」 | 最高 | 多步 Agent，跨 App |

①② 一周能用起来，而且每天真能用。③④ 是同一套 Agent 技术的两个深度，先做③的单步，再放开④。

**建议顺序：① → ② → ③ → 硬件 → ④。** 硬件放在③后面是因为硬件只替换「触发」这一环，前面稳了它才有东西可触发。

---

## 2. 语音识别：走本地，不走 Actionway

你问本地是不是不支持。恰恰相反，**本地是这件事最好的路**，原因是延迟和成本。听写要的是「说完半秒出字」，每天几百次，走云端每次都要上传等回包。

三个候选：

| 方案 | 条件 | 中文 | 延迟 | 成本 | 结论 |
|---|---|---|---|---|---|
| **Apple SpeechAnalyzer** | macOS 26 | 支持普通话和粤语 | 最快，比 Whisper small 快 3 倍 | 0 | **首选**，系统自带模型、不出网 |
| **whisper.cpp / WhisperKit** | 任意 Apple Silicon Mac | 好 | 短句约 0.5 到 1 秒 | 0 | macOS 26 以下的备选 |
| Actionway transcribe | 已装 | 未知 | 上传加排队，秒级 | 按次计费 | 不适合听写，它是给媒体文件用的 |

Actionway 的转写能力是「媒体理解」类，喂的是视频和音频文件，适合转一小时的会议录音，不适合每句话调一次。你充值的额度留给别的能力更值，比如后面④里要用到的 OCR 或搜索。

**要你确认的**：Mac 的 macOS 版本。26 就用 SpeechAnalyzer，否则 whisper.cpp。

## 3. 理解层：沿用 voice-router 的路由表

已经写好的 `voice_router/` 直接复用，意图表换成 Mac 的：

```
switch_app   → 切 App。参数：app 名
dictate      → 听写。参数：文本、是否润色
act          → 点东西 / 执行。参数：目标描述
chat         → 兜底
```

关键是**听写和命令怎么区分**。三种做法，我倾向第一种：

1. **两个快捷键**。一个键按住是听写，说什么打什么。另一个键按住是命令。用户自己分，零误判。
2. 一个键，靠模型判断。「打开微信」是命令，「明天三点可以」是听写。会有边界情况，比如你真想打出「打开微信」这四个字。
3. 唤醒词。「小 C，打开微信」。要常驻听麦克风，误触发多，硬件阶段再考虑。

听写模式不过模型，识别结果直接上屏，快。命令模式才走 Claude 抽意图。

## 4. 执行层：三件事三种工具

### ① 切 App
```
open -a "WeChat"
```
就这么简单。App 名的中英文对照放在路由表里，「微信」映射到 WeChat。

### ② 打字
两种方式：
- **模拟键盘敲**。逐字发键盘事件。中文走输入法会出问题。
- **剪贴板粘贴**。文本放进剪贴板，发一个 Cmd+V。中文、emoji、长段都稳。**用这个**。粘完把原剪贴板内容还回去。

### ③④ 点东西和执行任务
这一层的核心问题是 **Agent 怎么「看见」屏幕**。两条路：

| 路 | 原理 | 速度 | 成本 | 稳定 |
|---|---|---|---|---|
| **辅助功能树** | 读 macOS Accessibility API，拿到每个按钮的名字和坐标，按名字点 | 每步约 0.3 秒 | 只传文字，便宜 | 原生 App 很稳，Electron 和网页部分可用 |
| **截图视觉** | 截屏给模型看，模型算坐标点 | 每步 1 到 3 秒 | 每步传一张图 | 什么 App 都能用，但会点错 |

**用辅助功能树为主，截图兜底。** 现成的开源件是 [macos-use](https://macos-use.dev/)，MIT 协议，一个 Swift 二进制，MCP 协议，六个工具：打开 App、点、打字、按键、滚动、重读界面。每步只返回变化的元素，省 token。

Agent 本体不用自己写循环。两个选择：
- **Claude Agent SDK** 加 macos-use MCP。Claude Code 的那套 harness 打包成库，自带工具循环和权限。你本来就在用 Claude Code，登录复用。
- 自己用 Anthropic SDK 的 tool runner 写循环，工具就是 macos-use 那六个。更可控，代码多一些。

先用 Agent SDK，跑起来再说。

## 5. 安全：Agent 在你 Mac 上点东西这件事

这是必须先想清楚的，不是后补的。

- **听写和切 App 不需要确认**，这两个动作可逆。
- **点东西默认要确认**。Agent 说「我要点『删除』」，你说「嗯」它才点。发送、删除、付款、关闭未保存这几类永远确认。
- **App 白名单**。命令模式只能操作你列出来的 App，1Password、银行、系统设置不在里面。
- **一键停**。任何时候按 Esc，Agent 当步中断。
- 截图会传给模型。不想传的 App 加进黑名单，那些 App 只走辅助功能树。

## 6. 形态：先脚本，后菜单栏

| 阶段 | 形态 | 为什么 |
|---|---|---|
| 现在 | Python 脚本，终端里跑 | 复用 voice-router，改起来快 |
| 稳定后 | Swift 菜单栏小程序 | 全局快捷键更稳，开机自启，权限管理干净 |

Python 阶段需要的：麦克风录音、whisper 或调 SpeechAnalyzer、pyobjc 调系统切 App 和剪贴板、全局快捷键监听。都有现成库。

## 7. 硬件：换掉「按键」

硬件阶段做的事只有一件：**把「按住键盘上某个键」换成「按住一个实体按钮」或「对着一个盒子说」**。

- **最简单**：ESP32 一个按钮，BLE 模拟成键盘，按下发一个 F 键。Mac 那边零改动。一个周末。
- **进一步**：盒子自带麦克风，音频走 BLE 或 Wi-Fi 传到 Mac，Mac 识别。麦克风离嘴近，识别率高。
- **再进一步**：盒子上有个小屏，显示「听到了什么」和「准备做什么」，确认按钮在盒子上。

已有的 `firmware/esp32/` 是串口收命令点灯，方向反了，硬件阶段会重写成「硬件发触发给 Mac」。

---

## 8. 待你决定

1. **macOS 版本**是不是 26。决定语音识别走哪条。
2. **听写和命令用两个键还是一个键**。我倾向两个。
3. **先拿哪三个 App 试**。辅助功能树在不同 App 上表现差很多，先挑你每天用的。
4. **截图能不能传给 Claude**。能的话③的覆盖面大很多。
5. Claude 用什么登录。有 Claude Code 订阅就直接复用，没有就走 API key。

定了这五条我就把 voice-router 的意图表和出口换成 Mac 的，先把①②跑起来。
